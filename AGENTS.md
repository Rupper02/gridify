# AGENTS.md — GridForge

Guidance for AI coding agents (and humans) working in this monorepo. Read it before you change anything.

## What this is

GridForge is a pull-request workflow for grid connections on one real UK network: NGED's **Bicker Fen 132 kV GSP** (Lincolnshire), built only from open data. `main` is the network as it exists today. Not-yet-built projects sit in an optional registry; you branch, pull projects onto the branch, and a deterministic engine (pandapower AC power flow) decides which connect, in what order and year, and why the rest are deferred. The operator reviews a consequence diff and merges or discards it.

Deep docs (they are the spec, so keep them current):
- `README.md`: system, data sources, how a project is judged, API table, limitations
- `packages/optimizer/README.md`: engine algorithm, study cases, per-year evaluation and outages, suggestions, config
- `apps/pipeline/README.md`: Dagster asset graph and checks
- `apps/web/README.md`: planner files and behaviour (Vite + React + TypeScript).

## Commands

Prereqs: Node 22 + pnpm 10, Python 3.11+ with `uv`. No API key needed.

```bash
pnpm install                                      # repo root

# build the warehouse (the only way; there is no seed script)
cd apps/pipeline
uv run dagster asset materialize -m grid_simulator.definitions --select 'ltds_tables*'   # keep the quotes; offline
uv run dagster asset materialize -m grid_simulator.definitions --select 'ecr_register_fetch,ecr_editions,ecr_changes'  # live ECR fetch + diff
# never select 'pin_*' unless you mean to replace the pinned snapshot in packages/optimizer/.../data/nged/

# run (two terminals, repo root)
pnpm --filter @gridforge/api dev                  # http://localhost:8000
pnpm --filter web dev                             # http://localhost:3000

# test
pnpm test                                         # everything, via Turborepo
cd packages/optimizer && uv run pytest -q         # engine
cd apps/api && uv run --with pytest pytest tests -q   # API (uses a temp scenarios DB)
cd apps/web && pnpm test && pnpm typecheck        # UI unit tests + tsc
GRIDFORGE_TEST_PG_URL=postgresql://user@host:5499/db  cd apps/api && uv run --with pytest pytest tests -q   # + the Postgres store test
```

Keep suites fast: the engine suite stubs the N-1 screen (`tests/conftest.py`, opt in with `@pytest.mark.n1`), shares expensive runs per module and runs on 4 xdist workers (~2 min); the API suite uses small saturating fixtures (~2 min). Run suites one at a time, not alongside browser sessions.

- `uv run dg dev` (Dagster UI) also binds **port 3000**: don't run it alongside the web app.
- Re-materialise after changing `nged.py` or bundled data, and restart the API: it caches optimize results and the GSP boundary in memory.
- Narration and the agents are not optional: `OPENROUTER_API_KEY=...` in `apps/pipeline/.env` (the API loads it from there) is required, and the API refuses to start without it (`config.require_openrouter_key`). Never commit `.env`. The API launches the agent runtime (DBOS) on `apps/api/data/dbos.sqlite` (`GRIDFORGE_DBOS_URL`; Postgres when the scenarios store is Postgres). Recovery after a restart is pinned to `GRIDFORGE_DBOS_APP_VERSION` (default: the engine fingerprint), so set it in dev to keep in-flight runs across `--reload` restarts. The tests set a placeholder key and swap the narrator for a scripted one (`tests/conftest.py`), and `tests/test_agents.py` runs scripted models (`FunctionModel`) on a temp DBOS database: nothing ever reaches OpenRouter from a test.

Windows / Git Bash:
- Multi-line `python -c "..."` breaks; write a temp `.py` in your scratch dir and run it with `uv run python`. Long inline shell commands (roughly over 6 kB, e.g. a big heredoc) get truncated and fail with "unexpected EOF": write them to a file too.
- Don't shell-grep or `find` from the repo root: `node_modules` is huge. Use the Grep/Glob tools or scope to a package.
- `--select '*'` can still shell-expand here; use `'ltds_tables*'`, which already selects the full graph.

## Domain rules (non-negotiable; set by the owner)

1. **`main` = only what physically exists today.** Every not-yet-built project, and any future network asset, is an OPTIONAL registry item that counts only once it is added to a branch. Never pre-load, inject in the background, or reserve capacity for it.
2. **Physics is deterministic.** Feasibility comes from power flow only. An LLM never computes, scores or adjusts physics or ranking. What an LLM may do, all of it in the API and all through OpenRouter: narrate (`justify`, `narrate_diff`, `narrate_suggestion`, restating engine figures) and, in the agent harness (`apps/api/src/gridforge_api/agents/`), **plan studies, call deterministic engine tools, compare their outputs and phrase them**. Every figure in an agent finding, review or answer is bound to a recorded tool step: a finding names a `step_id` and an item index and the server copies the figures from the cached study (`EvidenceLedger.bind_findings`; anything else is sent back to the model); a review restates the merge gate's blockers by kind, element and fingerprint (an output validator enforces it); an answer's numbers are checked against the run's tool outputs (`check_numbers`, soft flags on the message). Agents never merge, discard or edit `main`; their proposals are deferred tools the operator approves (a branch, a reinforcement, a works window, a project or a change to one, a run of the branch). The key is mandatory: without `OPENROUTER_API_KEY` the API does not start, and nothing degrades to a key-less substitute (no scripted chats, no "agents off" state; `starting` is the only non-answering state, while the runtime launches).
3. **Parameters are set by the flows, not the operator.** No ranking-weight sliders or physics knobs in the UI; weights stay engine defaults in `config.py`.
4. **Two study cases plus the boundary.** Every accepted project must pass `winter_peak` (grown demand, winter ratings, PV/wind at nil, batteries charging at `import_mw`) AND `summer_min` (LTDS minimum-demand factor, not grown, summer ratings, everything at full export), plus the GSP export limit. Voltage limits are the statutory bands by level (`VOLTAGE_BANDS`), judged after the tap changers have settled (`_solve` regulates them; taps persist on the net). Every `Reason` carries the element, the value, the `limit` and the `case`. The N-1 screen (`n1_screen_cases`: the 132 kV backbone in each case of `config.N1_CASES`, winter peak and summer minimum, every finding carrying its `case`, islanded demand on the first case only; each outage the post-fault steady state: taps re-regulated, transformer loading against the LTDS emergency rating) is reported on `PhaseResult`, never a gate. Lines carry their LTDS charging (B1); the ranking's grid-need solve is the regulated, dispatched winter-peak case (`_run_case`), never a raw `pp.runpp`. Once the queue is decided, `years.evaluate_years` solves every plan year (2026..2035) as a fixed plan: demand interpolated to the year, the projects energised by then, both cases, N-1 in each of its cases and that year's planned outages (studied in their season's case(s), `config.SEASON_STUDY`). It never changes who connects; planned outages, like N-1, are reported, never a connection gate. **Merging is gated** (`gate.merge_verdict`, registry `MERGE_CHECKS`, every level in `config.MERGE_GATE_LEVELS`): a branch is refused when its result is stale, or when it introduces or worsens a problem relative to its parent in the same plan year (new or worsened overloads, new voltage breaches, the GSP newly over its limit, new N-1 findings, new demand-side breaches, works windows that become infeasible, a year that stops converging, a parent that moved on); what the parent already carries is context, never a blocker; warnings need `acknowledge`. The gate is a pure policy over existing results and never solves. Connections stay ungated.
5. **Real data, real units.**
   - Never hardcode a voltage or ratio: line MVA comes from `voltage_kv`, transformer ratios from `hv_kv`/`lv_kv`.
   - LTDS rows with Status `Removed` are excluded (the LTDS is a change-log against NGED's previous edition).
   - Cite sources (resource ids live next to the constants in `nged.py`).
   - Bundled ECR data must contain **no personal data** (customer names, addresses, MPANs are dropped by the fetch script).
   - **Imported grids** go through `sources.normalise_net` → `apply_import_meta` → `inspect_net` → `validate_net`, and nothing is filled silently: a blank rating is flagged `unrated_lines` (its loading is not checked), a missing minimum-demand factor or seasonal rating skips the summer case, a missing export limit means export is reported and never limited, GB bands and the N-1 scope are listed as assumptions. Every fallback is a `ModelAssumption` with a key in `sources._GENERIC` (or `nged._ASSUMPTION_TEXT` for the builder); a new one needs its text there and a line in the README register.
6. **Reasons are human-readable and actionable**: why it's blocked, and what to do. The engine emits typed reasons (`line`/`trafo`/`voltage`/`gsp`/`rejected`, ...); `normReason` (`apps/web/src/lib/reasons.ts`, re-exported from `src/api.ts`) turns them into `{kind, element, short, why, action}` (unit-tested in `src/api.test.ts`). To add a reason type: a check in `network.LIMIT_CHECKS`, a lever in `suggest.LEVERS` (and a reinforcer in `network.REINFORCERS` if it needs a new kind of upgrade), and a normaliser in `reasons.ts`'s `NORMALISERS`.
7. **Honesty over fake precision.** State limitations instead of modelling them badly: fault levels are not checked, the 400 kV network is context only, the GSP limit's sign convention is assumed, the tap step (1.25%), the tap-changer target (1.02 pu, chosen as the lowest that keeps today's network in band) and the per-case dispatch factors are planning assumptions (including demand and electrolyser projects drawing `DEMAND_PROJECT_MIN_FACTOR` = 50% of `import_mw` at summer minimum), N-1 is informational, planned works windows are reported without placing their weeks in the calendar (same-season windows are studied together), their curtailment is a bounded first-order search (`maintenance.py`, not an optimal re-dispatch), and a repowering changes only the later years, never the queue run, and the derate factor (50%) is assumed. A lever's "freed MW" is first-order (≈), and `connection_options` probes the plan's hardest phase, not every year, and says nothing about the works or cost of a new point of connection. Don't tune constants (e.g. `MAX_REINFORCE_STEPS`) for nicer-looking output. Every source and assumption is listed in the root README's *Sources and assumptions* register: a new or changed constant updates it in the same change.

## Design principle: SOLID

SOLID is a standing rule for all code here, not a cleanup pass. Apply it when you write or change code, and say so in review when a change bends it.

- **S: one reason to change.** A module or class owns one concern. HTTP routing, SQL, caching, job scheduling and narration are separate modules (see the `apps/api` layout above); the engine's ranking, trialling and queue-building are separate steps (`greedy._Run`). If a function needs "and" to describe it, or passes ~100 lines, split it.
- **O: extend by adding, not editing.** Variation points are data or registries, not `if kind == ...` ladders. Study cases are `network.CASE_SPECS` entries; a new case is one entry plus its dispatch factors in `config.py`. When you add a branch on a type string in a second place, make it a registry instead. Registries in place: `CASE_SPECS`, `LIMIT_CHECKS`, `REINFORCERS`, `OUTAGE_APPLIERS`, `maintenance.WORKS` / `REPOWERERS`, `demand.ALERT_CHECKS`, `config.SEASON_STUDY`, `suggest.LEVERS`, `gate.MERGE_CHECKS` (levels in `config.MERGE_GATE_LEVELS`), `findings.EXTRACTORS`, `studies.STUDIES`, `sources.SOURCES` (a new file format is one `SourceSpec`), the harness's `roster.AGENTS`, `events.TRIGGERS`, `tools.TOOL_GROUPS`, `workflows.WORKFLOWS` and `streaming.STAGE_BY_TOOL_PREFIX` (mirrored by the web `trace.STAGE_BY_TOOL_PREFIX`), the web `NORMALISERS`, `ask.PROPOSAL_EFFECT` (what an approved proposal refreshes, by tool) and `SidePanel`'s `TABS`, and the per-technology tables `theme.TECH` and `ui.tsx`'s `TECH_ICON` (typed `Record<Tech, …>`, so a new technology fails to compile until it has an entry).
- **L: substitutable implementations.** Anything behind a `Protocol` (`Narrator`) or a callable seam (`net_factory`, `progress`) must work with any implementation that honours the contract, including a no-op one (`NoNarrator`). Don't add `isinstance` checks or special cases for one implementation.
- **I: small, role-shaped interfaces.** Depend on the narrowest thing you use: a function takes a cursor, not the store; a component takes the props it renders, not the whole planner state. Don't grow `PlannerState` or a Protocol for one caller's convenience.
- **D: depend on abstractions, wire in one place.** Collaborators (warehouse, store, cache, narrator, net factory) are passed in as arguments. Only `deps.py` (API) and the entry points construct concrete instances. Engine functions take `net_factory=` rather than calling `build_base_net()` directly; new engine code must do the same. No new module-level mutable state outside `deps.py`.

Pragmatism: SOLID serves the code, not the other way round. Don't add an interface for something with one implementation and no test or deployment need to vary it (a Protocol earns its place at an LLM, network or database boundary). Prefer a small function over a class hierarchy. Keep the physics and ranking rules in Domain rules above untouched by refactors: a SOLID change must not change engine output (the suites prove it).

## Engineering conventions

- **Tests are grid-agnostic.** Derive fixtures from `build_base_net()` via `packages/optimizer/tests/_grid.py` (`stiff_bus`, `weak_buses`, `saturating_candidates`, `grid_deferred`, `invalid_bus`). Never hardcode bus ids, and never size fixtures from policy caps like `MAX_CONNECTION_MW` (only use the cap to test the cap itself). NGED-specific data rules go in `tests/test_nged.py`.
- **API cache keys include the candidate-set hash, the project's baseline and the engine fingerprint** (`cache.cand_key`, `Projects.baseline(pid)` (the warehouse snapshot id for NGED, the file fingerprint for an import), `ResultCache.engine` → `ResultCache.key(kind, params, ckey, baseline, extra)`). `BranchInputs` carries the branch's `project_id`, `baseline` and `net_factory` (the project's network with the branch's reinforcements), so `PlanService` never reaches for a global network. Results live in the scenarios DB table `result_cache` (durable) and in `ResultCache.compute` / `.payload` (process). Any new cached computation must use `ResultCache.key`, or branches serve each other's results / stale physics survives a code change. The engine's `trial_cache` dicts are keyed the same way (`ResultCache.trial_cache`). Branch reinforcements join the optimize key (`service.reinf_key`); the per-year results (kind `years`) add the outages and the schedule (`service.years_key`), so editing those re-solves the years but not the queue. The diff's planned-works study (kind `works`, `PlanService.works_on_plan`) keys the parent's plan with the branch's outages swapped in. Every engine result is read through `ResultCache.through` (in-process dict → durable table → compute), and the merge gate's freshness is `ResultCache.has` on those same keys (`PlanService.freshness`): never derive it from timestamps. Studies (`PlanService.study`) are cached the same way under `study:<kind>` with the study's parameters in the key, so a chunk (a study with its own parameters) caches on its own. The payload's `run_key` is the plan-years key: the identity a review or an agent event refers to. Agent steps store the cache key of what they ran; `EvidenceLedger.replay` re-reads it and flags `stale` when the engine has changed.
- **Agent work is DBOS workflows** (`agents/workflows.py`): bounded by `config.AGENT_RUN_BUDGET`, idempotent by workflow id (`<workflow>:<dedup id>`, from `events.TRIGGERS`, so a cached re-run or a repeated event never wakes anyone twice), every side effect in a step. `Harness.durable(name, fn)` is `DBOS.run_step` inside a workflow and a plain call outside one, so tools, validators and tests run without DBOS. Workflow code reads only its arguments and step outputs; collaborators come from the runtime (`workflows.RUNTIME`, set by `AgentRuntime.launch`), never from `deps`. Every tool call goes through `tools._recorded` (an `agent_steps` row with its arguments and cache key, a payload that always carries `step_id`); agent solves go through `SolverGate`, taken **per chunk** of a study (`PlanService.study(hold=)`): an operator's job gets the solver between chunks, not after a whole hosting-capacity sweep; the warm-up never takes the lock. A study outside an agent's remit or over its solve budget is refused in the tool's answer (a payload the model reads), never raised: a raised retry twice over ends the run. One failed specialist is a line in the steward's brief, not the end of the sweep. A review is stored only while its run is still the branch's current one (`freshness().years_key`), so a slow review of an earlier run never becomes current. A new agent is one `AgentSpec`, a new trigger one `Trigger`, a new study tool appears by itself from `studies.STUDIES`. The SSE route reads the stream with DBOS's blocking reader in a worker thread, on purpose (the async reader shares one executor across event loops).
- **Long computations run on the single job worker** (`JobRunner.start(kind, fn(progress, publish))`, `GET /jobs/{id}`); the planner polls. `publish(partial)` stores a partial result on the job record (`GET /jobs/{id}?partial=true`, `has_partial`): the optimize job publishes the queue, then each year as `evaluate_years(on_year=...)` lands, the body's `view_year` first. Keep the sync endpoints too (tests and scripts use them). The engine reports progress through `optimize(progress=...)` and `evaluate_years(progress=...)` (the API maps them to 0..0.5 and 0.5..0.95, narration at 0.95); new long stages should call it (it is also where cancellation lands: `POST /jobs/{id}/cancel` makes the next progress report raise `JobCancelled`). Plan years are cached by `years.year_signature` (`ResultCache.year_cache`), so an edit re-solves only the years it touches; a new input to a year's result must go into that signature.
- **The warehouse is read-only to the API.** Anything a user does goes to the scenarios DB. Schema changes there need a migration (a `con.columns()` check + ALTER, dialect-aware) and, for per-project columns, an entry in `_ADDED_COLS` so they copy on branch create/merge.
- **Change the output shape in one pass:** `types.py` → API enrichment in `apps/api/src/gridforge_api/service.py` → `apps/web/src/types.ts` + `src/api.ts` → the component that renders it. Add an API test for new endpoints.
- Engine functions (`optimize`, `evaluate_years`, `suggest_unblock`, `diff_results`) make no network calls; keep it that way. Network/LLM calls belong in `llm.py` and the API only.
- Delete dead code rather than keeping it "not wired". Update the READMEs in the same change when behaviour, endpoints or commands change.
- pandapower gotchas: generation is injected as PQ `sgen` (not `gen`) so voltage problems show; use `pandapower.toolbox.drop_buses`; avoid `deepcopy` of nets in hot loops (build once per phase, inject/roll back); in pandapower 3 a transformer's taps are inert unless `tap_changer_type="Ratio"` is set; the LTDS tap ranges (e.g. -12..+4) are HV-winding taps where a lower tap raises the LV voltage, so model them with `tap_side="hv"`; `sgen` rows carry `p_rated_mw` and `import_mw` (set by `inject_sgen`) that `dispatch_for_case` reads.
- The root `.gitignore` is a Python template that ignores every `lib/`; `apps/web/src/lib/` is explicitly un-ignored. Check `git status` shows new frontend files before committing.

## Planner (`apps/web`)

- State lives in one object (`PlannerState`, `hooks/planner/core.ts`; `patch` merges partial updates; `ref.current` is the latest state for async flows). `usePlanner` only composes the hooks under `hooks/planner/` (`useRun`, `useBranchList`, `useBranchFlows`, `useRegistry`, `useSelection`, `useProjectEdits`, `useMaintenance`, `useFindings`, `useAgents`, `useAsk`, `useDerived`), each of which takes the shared `Core` plus only the other hooks' actions it needs. Put a new flow in the hook that owns its concern, or a new hook; don't grow `usePlanner`. Components never take the whole `Planner`: each declares the slice it reads with `PlannerSlice<state keys, action keys, derived keys>` (+ `WithPatch` / `WithMap` / `WithFormInvalid` when needed, `hooks/planner/slice.ts`) and exports it as e.g. `QueueTabPlanner`; a parent's slice is the intersection of its children's (`SidePanelPlanner`, `MapViewPlanner`). Reading a field outside the slice fails to compile, so add the key to the slice when you use a new field. Only `App.tsx` (the composition root) sees the full `Planner`. Known limit: `patch` is still a free-form setter, so what a component may write is not narrowed. Actions that need state React hasn't flushed yet take an explicit override (e.g. `run({ activeBranch })`) instead of reading it back.
- Engine runs take ~20 s (two study cases) before the years. `run()` keeps its in-flight flag in a ref and coalesces overlapping requests into one re-run; a failed call clears the flag and toasts. Keep that pattern for any long call; never drop requests silently.
- **Projects in the planner.** `s.projectId` is the active project and `derived.mainId` its plan-of-record branch (`lib/projects.mainIdOf`): never write `"main"` for a branch id in a hook or component (the word *main* in copy is fine: every project's plan of record is called that). `useProjects` boots the planner (the projects, then the default project's model and branches, then its main's run; the boundary card loads on its own, since on a cold API it is a full power flow) and switches projects by resetting everything that belonged to the previous one (`FRESH`). Loading is told, not assumed: the result stamp says *Loading the grid…*, a step that fails is retried with a growing pause (`lib/boot.ts`: the API still starting, or restarting under `--reload`) and then shown on the stamp with a Retry, never only as a toast. What a project cannot do is hidden by `derived.caps` (`project.capabilities`): no boundary card without a boundary, no Demand layer without demand groups, no registry section without a registry; a `synthetic` model (`model.crs`) gets a blank basemap (`MapView` is keyed by `crs`, so it remounts) and a note under the result stamp.
- The agents in the planner: `useAgents` polls `GET /projects/{pid}/agents` every 15 s (and a branch's reviews with it, since the reviewer comments a few seconds after a run); `useAsk` keeps one open `EventSource` per reply (`api.streamReply`), folds its events into `s.trace` while it streams and re-reads the stored message when it ends; a reply's proposals are decided one by one and the answer resumes once all of them are (`waiting_for` until then); the planner then polls the thread until the continued answer settles and refreshes what every approved proposal touched (`lib/ask.ts` `PROPOSAL_EFFECT`: a run shows the agent's run, which is the branch's run and cached; a project or a change to one re-reads the branch's stored projects (`GET /branches/{id}/candidates`, `s.candidates`) and the result shows as out of date; a reinforcement or a works window re-reads them and applies the edit policy); `cancelReply` stops a reply (`POST .../threads/{tid}/cancel`). The side panel's first tab is `ask` (the `Tab` key; label *Ask*) and it is the planner's **only** conversation: no scripted or deterministic chats, ever; every suggested question (`lib/ask.ts` `suggestedQuestions`, from what is in view) and every card button (*Ask the agents how it could connect*) goes to the answerer. The only non-answering state is `starting` (the API's runtime not launched yet): the pill says so and the composer waits.
- Runs are explicit. Adding a project (from the registry, or an agent's approved proposal) makes it Preliminary until the next run; changing the demand profile or a reinforcement marks the shown result stale (**Re-run**); a works window or an energisation year refreshes quietly by itself (`lib/refresh.ts` `EDIT_POLICY`). The year slider **never** starts a run: every run solves all years, and the slider only switches between them (years still arriving as partial results show as solving).
- Pure logic goes in `src/lib/` or `src/api.ts` with a vitest next to it; components stay thin. Styles are classes in `src/styles.css`; inline styles only for data-driven colours.
- `MapView.tsx` owns the MapLibre instance: layers/icons are added once on `load`, data is pushed with `setData` from the memoised GeoJSON in `App.tsx`, and the HTML overlay (`MapMarkers`: project markers, substation names, loading/diff/outage tags) is re-projected on each `move`.
- Verify before claiming done: `pnpm --filter web typecheck && pnpm --filter web test && pnpm --filter web build` (the typecheck fails on unused locals and parameters: delete them, don't suppress), then drive the dev server against a running API in the owner's real Chrome (the `claude-in-chrome` tools: look at every screen as a QA engineer would, read the console) and require **zero page errors**; a scripted headless browser (Playwright in a scratch dir, `--use-gl=swiftshader`) is a fallback, not the check, and never with an emulated viewport. Exercise the flow you changed (branch → add project → run → scrub the years → review; for the agents: ask → the trace → a proposal → approve → the planner refreshes). Note that `uvicorn --reload` only restarts after the current job and the agent runtime have shut down: after an API edit during a long solve, check the log for "Application startup complete" before trusting what you see, or restart the API.
