# GridForge web

The planner UI ("GridForge Glass", designed in `docs/design/gridforge-glass/`): a single-page **Vite + React 19 + TypeScript** app around a full-bleed MapLibre map, with floating panels on top. It talks to the FastAPI service in `apps/api` and has no server of its own.

| Path | Role |
|---|---|
| `src/App.tsx` | The composition root: the only file that sees the full `Planner`. Lays out the header, left cards, map, roadmap dock and side panel; derives the map's GeoJSON from state |
| `src/hooks/usePlanner.ts` | Composes the hooks under `src/hooks/planner/` into one `Planner` |
| `src/hooks/planner/` | `core` (the `PlannerState` object and `patch`), `slice` (the `PlannerSlice` types components declare), `useRun` (jobs, partial results, cancelling a superseded job, quiet runs), `useAutoRefresh` (edits the policy in `lib/refresh.ts` marks automatic re-run quietly), `useBranchFlows`, `useBranchList`, `useRegistry`, `useSelection`, `useProjectEdits`, `useMaintenance` (planned works), `useMapFeatures` (the colouring layer and which kinds of element the map shows), `useCopilot` (intake chat, recommendations, try-a-lever, maintenance windows), `useFindings` (the findings ledger and the operator's call on each finding), `useAgents` (the agents' status poll and pause switch, a branch's reviews, the evidence drawer), `useAsk` (conversations with the answerer agent: a streamed reply, approvals), `useProjects` (the boot, switching projects, import, delete, the model's assumptions), `useDerived` |
| `src/api.ts` | Typed client for the API; re-exports `normReason`. A failed call throws `ApiError` with the status and the API's `detail` (a refused merge's verdict, for one) |
| `src/lib/` | Pure helpers, with vitest next to them: `mapFeatures` (the registry of element kinds the Show menu toggles, remembered per browser), `derive` (queue and year derivations), `maintenance` (planned works in words: the schedule form body, tags, the verdict registry and its plain-English detail), `intake` (the Copilot's New project conversation), `maintCopilot` (the Maintenance conversation: element, work, duration, best window or a named one), `recs` (Recommendations wording and lever actions), `runStages` (job stage to overlay step), `layout` (laptop breakpoints), `demand` (demand regions: state colours, alert summary, P2/8 class wording, halo geometry), `reasons` (the reason normaliser registry), `diff` (the per-year diff: Review sentences, map deltas, planned works wording), `gate` (the merge gate's state for the Merge buttons, the refused-merge body, finding titles, grouping by year and where a finding points on the map), `trace` (a streamed reply folded into text and stage chips, tool and stage names, the evidence line, a superseded review, the agents pill), `projects` (a project's main branch, capability chips, the import report in lines, the known-limit fields), `geo` (GeoJSON), `icons` (canvas map icons) |
| `src/components/` | `Header` (branch picker, demand profile, Run / Re-run), `LeftCards` (result stamp and readings), `MapView` (MapLibre), `MapMarkers`, `MapControls`, `DetailCards` (project and element cards), `WindowVerdict` (a works window's verdict chip and detail), `RegionCard` and `RegionLabels` (the Demand layer), `Roadmap` (year slider dock), `ProjectsScreen` (the projects and the import form), `SidePanel` (a typed `TABS` registry: adding a tab is one entry) → `AskTab` (the picker and the Ask chat; the three guided chats live in `CopilotTab`) / `QueueTab` / `OutagesTab` / `FindingsTab` (agent findings carry an *evidence* link) / `ReviewTab` (the diff, *Merge readiness*, then the reviewer's comment), `StudyDrawer` (the study behind a step an agent cited), `RunOverlay`, `ui` (shared bits: `TechIcon`, toggles, steppers, diff tiles); the header carries the agents pill |
| `src/theme.ts`, `src/styles.css` | Status, technology (`TECH`) and branch-hue colours, and the stylesheet |

## How it behaves

- **Cheap edits refresh by themselves; queue edits wait for Run** (`lib/refresh.ts` `EDIT_POLICY`). Scheduling a works window or changing an energisation year re-solves only the years it touches (the API's per-year cache) in a quiet run: no overlay, the stamp says it is updating. Adding a project (Preliminary until the next run), changing the demand profile or adding a reinforcement re-decides the queue, so the result shows as out of date (the button reads **Re-run**) until you run. A newer run cancels the one in flight.
- **The year slider never runs.** Every run solves all years 2026 to 2035; the slider switches between them. While a job runs, the queue and each year appear as the API publishes them, the year in view first. The run overlay follows the job's real stages.
- **Branches.** Each branch has its own hue, which frames the map. `main` is read-only for proposals (outages and reinforcements need a branch), but its demand profile stays editable: a deliberate departure from the design.
- **Projects.** The capsule next to the logo names the project the planner is on and opens the projects screen: the built-in NGED project and every import, with Open and Delete, and the import form. Drop a CIM/CGMES zip, a pandapower JSON or a MATPOWER case, name it, and optionally enter what you know and the file does not carry (an export limit, a minimum-demand factor, seasonal rating ratios; recorded as entered by you). The API validates it and the screen shows the report (counts, the study cases, warnings, what the model assumes or lacks) before *Open project*. An open project drives everything: its map (a synthetic layout gets no basemap and a note), its branches and main, its queue, the gate, the ledger and the agents. What a project cannot do is hidden rather than faked: no boundary card without a boundary, no Demand layer without demand groups, no registry without one. *What the model assumes* under the result stamp lists the assumptions for every project, NGED's included.
- **Ask the model.** The first tab. With an OpenRouter key on the API, *Ask anything* opens a conversation with the answerer agent on the active branch: the reply streams in with its planning stages as chips (Plan · Assemble · Run · Check · Cite), each tool call carrying its step id; a study chip opens the **evidence drawer** (the study re-read from the durable cache, its items with the engine's figures, what it did not study, a stale notice when the engine has changed since). The text ends with an evidence line (branch, snapshot, steps, engine); a figure no tool produced is flagged under it. A proposal the agent makes (a branch, a reinforcement, a works window) appears as a card with Approve / Deny; approving runs it on the branch and the answer continues. The picker also lists the conversations on the branch and the project's health thread (the steward's briefs), and the agents' status line with a Pause / Resume switch. Without a key the card is disabled with the reason and everything else works. The header pill says *agents off · idle · running · paused* and opens this tab.
- **Copilot.** *New project* is a guided intake that drafts a project and adds it to the branch; *Maintenance* asks for the element (the selected one, or the most loaded in the viewed year, or typed: `line 16`, `T30`, `EX-3000`, a place), the work and its duration, then either asks the engine for the best window (`POST /branches/{id}/works/best-window`, a job; ranked window cards with *Schedule on &lt;branch&gt;*) or schedules the season and year named (on `main` it opens a branch first). Free text is parsed by fixed rules, no LLM; *Recommendations* lists the levers for deferred projects, and *Try on &lt;branch&gt;* stores a lever as a simulated reinforcement for the next run to measure (on `main` it opens a new branch first).
- **Show menu.** Next to the Deferred switch, *Show* lists every kind of element the map draws (132 kV, 33 kV and lower lines, transformers, substation names, busbars, generation today, projects, planned works, loads, demand groups) with a switch each; the crosshair shows only that kind (press it again for the usual set), and *Show all* restores the defaults. A hidden kind is left out of the map entirely, tags and clicks included. The choice is remembered in this browser (`localStorage`, a convenience only). Demand groups are off by default; the Demand layer turns them on.
- **Demand layer.** The fourth map layer draws every demand group (an LTDS Table 3 primary, or a BSP over the primaries it feeds, drawn at its own busbar) as halos at its substations, sized by demand and coloured by its worst alert in the viewed year (red breach, amber warning, neutral within limits), with "demand / firm MW · class" labels. Clicking one opens the region card: its P2/8 class in plain English, demand against firm capacity, firm headroom, the demand one 132 kV outage would cut off (and which), load buses outside the voltage band, ≈ room for new demand and the year's alerts. The readings card shows a *Customer alerts* line (breaches and warnings that year) that opens the layer on the worst region. Every figure is the engine's; it is a simplified P2/8-style check in MW (no customer counts, no restoration times or switching), and the card says so.
- **Review shows what merging changes on main.** Merge replaces main's planned works and reinforcements with the branch's, so *Merging changes on main* lists those the merge adds (+) and removes (−), from the diff's `on_merge`.
- **Merging is gated.** After every run the planner asks `GET /branches/{id}/merge-check` and *Merge readiness* shows the verdict: blockers in red (what this branch introduces or worsens in some plan year, each naming the element and the year), warnings in amber, and what main already carries folded away as context. Merge is enabled only when the verdict is ready or has warnings alone; its tooltip and the header's Merge button carry the state (red when blocked or out of date). With warnings, Merge opens a confirm step that lists them and *Merge anyway* sends `acknowledge: true`. A refusal from the API (409) is shown in the same card and toasted; nothing changes on main. A result the planner knows is out of date reads *Re-run before merging* whatever an older check said.
- **Findings** (the fifth tab, a departure from the four-tab design) lists what the branch's last run found, from the API's ledger: overloads, voltages outside the band, the GSP against its limit, N-1 findings, customer alerts, planned works that aren't simply feasible, the projects the run holds back and schedules against the recommendation, grouped by plan year with the breaches first; the tab's badge counts the open breaches. A row sets the year and focuses the element, project or demand group on the map; the tick acknowledges a finding (it leaves the open list; the next run keeps its figures fresh) and the filter shows the acknowledged and resolved ones. Every figure is the engine's.
- **Outages** lists the planned works on a line, transformer or existing generator, grouped by year with a summary line. The element card schedules them: *Maintenance* (full outage or derate to 50%), *Repowering* (uprate by 1.25x to 4x, or a parallel circuit / second unit, applied to the years after the window; the queue is not re-run for it) or *Replacement* (back like-for-like). Once a run studies a window it shows the engine's verdict (Feasible, Curtailment, Demand at risk, Not feasible) with the curtailed generators by name, MW and case, demand at risk, the windows studied with it, the N-1 screen during it and what the work leaves behind; map tags and roadmap chips carry the work type and are bordered in the verdict colour. **Review** shows the consequence diff against `main`: the 2030/2035 tiles, the network effect of the year on the timeline (its year picker moves the planner's year; a dot marks years where something gets worse), and the planned works with their verdict on `main` vs the branch. Diff mode tags the viewed year's line and transformer loading changes on the map.
- Icons come from `@phosphor-icons/react`.

```bash
pnpm --filter web dev        # http://localhost:3000  (needs the API: pnpm --filter @gridforge/api dev)
pnpm --filter web test       # vitest: reason normalisation, derivations, demand regions, Copilot intake and recommendations, run stages, the merge gate and findings, the agents' trace, projects
pnpm --filter web build      # tsc --noEmit + vite build -> dist/
```

The API origin defaults to `http://localhost:8000`; set `VITE_API_BASE` to point elsewhere.
