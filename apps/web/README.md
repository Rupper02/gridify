# GridForge web

The planner UI ("GridForge Glass", designed in `docs/design/gridforge-glass/`): a single-page **Vite + React 19 + TypeScript** app around a full-bleed MapLibre map, with floating panels on top. It talks to the FastAPI service in `apps/api` and has no server of its own.

## How it behaves

- **Cheap edits refresh by themselves; queue edits wait for Run** (`lib/refresh.ts` `EDIT_POLICY`). Scheduling a works window or changing an energisation year re-solves only the years it touches (the API's per-year cache) in a quiet run: no overlay, the stamp says it is updating. Adding a project (Preliminary until the next run), stating its control mode on the project card (a power factor or voltage control, as its connection offer sets it; until then the card says it is not stated and runs at unity power factor), changing the demand profile or adding a reinforcement re-decides the queue, so the result shows as out of date (the button reads **Re-run**) until you run.
- **One run at a time, restarted only when the inputs changed.** Every way a run starts (Run, an edit's quiet refresh, a branch or project switch, an approved proposal, the boot) goes through one state machine (`s.run`, `lib/runStages.ts`), written only by `useRun`. A request for the branch already on its way starts no new job (a loud one shows the card of a quiet one); a request made after an edit (`s.editedAt` later than the run's `requestedAt`: a profile change, a works window, a project) retires the job in flight and starts one with the current inputs, so nobody waits a minute for a result that is already out of date; a request for another branch supersedes. The card stays for the whole loud run, centred over the map above the roadmap; a failed or stopped run stays on the stamp with a Retry.
- **The year slider never runs.** Every run solves every plan year (2026 to 2035 today); the slider switches between them. The planner writes no plan year itself: the years and the two phases' horizons come from `GET /forecasts` at boot (`lib/plan.ts`: the bounds, the phase titles, the roadmap bands). While a job runs, the queue and each year appear as the API publishes them, the year in view first. The run overlay follows the job's real stages.
- **Branches.** Each branch has its own hue, which frames the map. `main` is read-only for proposals (outages and reinforcements need a branch), but its demand profile stays editable: a deliberate departure from the design.
- **Projects.** The capsule next to the logo names the project the planner is on and opens the projects screen: the built-in NGED project and every import, with Open and Delete, and the import form. Drop a CIM/CGMES zip, a pandapower JSON or a MATPOWER case, name it, and optionally enter what you know and the file does not carry (an export limit, a minimum-demand factor, seasonal rating ratios; recorded as entered by you). Choosing the file reads its voltage levels, and the form then asks for the study basis, which the import needs: peak demand's growth on the year before for every plan year (1.02 = +2 %, with what it adds up to by 2030 and 2035 shown under the table; Standard, optionally Low and High, which become that project's demand profiles), the lowest voltage the N-1 screen covers (each choice shows what it covers) and the voltage limits at every level (GB ESQCR and EN 50160 presets fill the boxes). The API validates it and the screen shows the report (counts, the study cases, warnings, what the model assumes or lacks) before *Open project*. An open project drives everything: its map (a synthetic layout gets no basemap and a note), its branches and main, its queue, the gate, the ledger and the agents. What a project cannot do is hidden rather than faked: no boundary card without a boundary, no Demand layer without demand groups, no registry without one. *What the model assumes* under the result stamp lists the assumptions for every project, NGED's included.
- **Ask the agents.** The first tab, and the planner's only conversation: there are no scripted chats. *Ask anything* opens a conversation with the answerer agent on the active branch: the reply streams in with its planning stages as chips (Plan · Assemble · Run · Check · Propose · Cite), each tool call carrying its step id; a study chip opens the **evidence drawer** (the study re-read from the durable cache, its items with the engine's figures, what it did not study, a stale notice when the engine has changed since). The text ends with an evidence line (branch, snapshot, steps, engine); a figure no tool produced is flagged under it. A proposal the agent makes (a project or a change to one, a reinforcement, a works window, a run of the branch) appears as a card with Approve / Deny, phrased in words (*Resize ECR-83EF2 to 55 MW (its import follows) on skegness-solar-qa*, *Add a parallel circuit on Bicker Fen to Boston 132 kV, circuit 1 (line 0)*: elements and buses by name through the model, branches by name; `lib/ask.ts` `PROPOSAL_TEXT`, a registry by tool; the arguments as given stay on hover, and a tool the registry does not know shows them as given); approving applies it on the branch, the answer continues, and the planner refreshes what it touched (a run shows the agent's run, which is the branch's run; a project change re-reads the branch's stored projects and the result shows as out of date until you run). *Stop* cancels a reply on its way. The picker suggests questions from what is in view (the first project deferred on the grid, the selected project's options or the selected element's best window, the viewed year's works, the GSP), lists the conversations on the branch, and the agents' status line with a Pause / Resume switch; the project card's *Ask the agents how it could connect* and a deferred project's *Ask what it would take* in the Limits tab send that question. The header pill says *agents starting · idle · running · paused* and opens a popover with the project's last twelve agent runs (agent and kind, status with a live elapsed time while it runs, branch, elapsed, `$` cost, solves, the summary's first sentence or the error), the spend today and in all, Pause / Resume and a way to the conversation; the runs are read only while the popover or the Review tab shows them (with the 15 s status poll). The API requires the OpenRouter key, so there is no "off".
- **Show menu.** Next to the Deferred switch, *Show* lists every kind of element the map draws (132 kV, 33 kV and lower lines, transformers, substation names, busbars, generation today, projects, planned works, loads, demand groups) with a switch each; the crosshair shows only that kind (press it again for the usual set), and *Show all* restores the defaults. A hidden kind is left out of the map entirely, tags and clicks included. The choice is remembered in this browser (`localStorage`, a convenience only). Demand groups are off by default; the Demand layer turns them on.
- **Demand layer.** The fourth map layer draws every demand group (an LTDS Table 3 primary, or a BSP over the primaries it feeds, drawn at its own busbar) as halos at its substations, sized by demand and coloured by its worst alert in the viewed year (red breach, amber warning, neutral within limits), with "demand / firm MW · class" labels. Clicking one opens the region card: its P2/8 class in plain English, demand against firm capacity, firm headroom, the demand one 132 kV outage would cut off (and which), load buses outside the voltage band, ≈ room for new demand and the year's alerts. The readings card shows a *Customer alerts* line (breaches and warnings that year) that opens the layer on the worst region. Every figure is the engine's; it is a simplified P2/8-style check in MW (no customer counts, no restoration times or switching), and the card says so.
- **Review shows what merging changes on main.** Merge replaces main's planned works and reinforcements with the branch's, so *Merging changes on main* lists those the merge adds (+) and removes (−), from the diff's `on_merge`.
- **The engineer's note.** After every run (main's included) one model call writes a note on it from the engine's digest of the run (`GET /branches/{id}/note`; at most 150 words, no step ids), a few seconds to a minute after the run lands. The Review tab shows it under *Merge readiness* (on main, under the plan-of-record line) as the answers render (markdown, elements named), with any figure the digest does not carry as a muted *not in the digest* chip, and says where it stands: *Writing the note… (48s)* while a `digest` run is live for the branch (from the runs list, with a live elapsed time), *The note is for an earlier run; the next run writes a new one* when its run key is not the shown result's, *No note yet: it is written a few seconds after a run* when there is none and nothing runs. It is read after every run and every 15 s while the Review tab shows.
- **Merging is gated.** After every run the planner asks `GET /branches/{id}/merge-check` and *Merge readiness* shows the verdict: blockers in red (what this branch introduces or worsens in some plan year, each naming the element and the year), warnings in amber, and what main already carries folded away as context. Merge is enabled only when the verdict is ready or has warnings alone; its tooltip and the header's Merge button carry the state (red when blocked or out of date). With warnings, Merge opens a confirm step that lists them and *Merge anyway* sends `acknowledge: true`. A refusal from the API (409) is shown in the same card and toasted; nothing changes on main. A result the planner knows is out of date reads *Re-run before merging* whatever an older check said, and a run that did not finish reads *Re-run before merging: the last run did not finish* with a Retry that runs it.
- **Limits** (the fifth tab, a departure from the four-tab design) is the engine's own answer to *what limits this branch* (`GET /branches/{id}/limits`, the engine's reduction of the last run; a 409 `not_solved` is asked again for about half a minute, then shown with a Retry). *What limits <branch>* and one line of counts, then: the **binding set**, the first eight elements that bind or come near a limit (a dot red for over, amber for near; the name and kind; the worst figure with its study case and year; *breaches from* or *near from* a year; the MW of room; *holds back ECR-…* chips; how many N-1 outages breach it; a sparkline of its figure over the plan years with the limit dashed), *Show all N* for the rest; a row sets the year to its worst and focuses the element (a bus through its demand region or a line on it). **Deferred projects**: one card per chain, in queue order (the id, technology and MW; *Deferred:* the engine's message with elements named; the binding element as a link, its case and phase, from when it binds; what the probe found when the engine studied it, what fits at its own busbar, whether parallel circuits reach its full MW and the best move, else *Ask what it would take*, which sends the question to the agents). **Causes**: the first six N-1 clusters (one weak link many outages overload, an island, a collapse: the label, rows, years, worst figure and cases; a weak link focuses its element), *Show all K*. **Planned works**: each window's verdict chip, element, year, curtailed MW, demand at risk and second faults when any. The tab's badge counts the elements over a limit, else the projects deferred. Folded at the bottom, **All findings · N rows** holds the ledger: one row per finding per plan year, folded into one group per finding (kind, element, case and what else identifies it) by criticality and then by kind, with the years it spans and the worst year's figure (the largest loading or MW, the voltage furthest from 1.0 pu); a group opens to its per-year rows; a row sets the year and focuses the element, project or demand group; the tick acknowledges a finding (all its years at once from the folded row) and the filter shows the acknowledged and resolved ones. The readings' N-1 stat opens this tab with the ledger unfolded on the N-1 group. Every figure is the engine's.
- **Outages** lists the planned works on a line, transformer or existing generator, grouped by year with a summary line. The element card schedules them: *Maintenance* (full outage or derate to 50%), *Repowering* (uprate by 1.25x to 4x, or a parallel circuit / second unit, applied to the years after the window; the queue is not re-run for it) or *Replacement* (back like-for-like). Once a run studies a window it shows the engine's verdict (Feasible, Curtailment, Demand at risk, Not feasible) with the curtailed generators by name, MW and case, demand at risk, the windows studied with it, the N-1 screen during it and what the work leaves behind; map tags and roadmap chips carry the work type and are bordered in the verdict colour. **Review** shows the consequence diff against `main`: the 2030/2035 tiles, the network effect of the year on the timeline (its year picker moves the planner's year; a dot marks years where something gets worse), and the planned works with their verdict on `main` vs the branch. Diff mode tags the viewed year's line and transformer loading changes on the map.
- Icons come from `@phosphor-icons/react`.

```bash
pnpm --filter web dev        # http://localhost:3000  (needs the API: pnpm --filter @gridforge/api dev)
pnpm --filter web test       # vitest, logic and invariants only (never wording, colours or layout): reason normalisation, derivations, demand regions, the suggested questions, run stages, the merge gate and findings, the agents' trace and the note's state, projects, planned works
pnpm --filter web build      # tsc --noEmit + vite build -> dist/
```

The API origin defaults to `http://127.0.0.1:8000` (not `localhost`: uvicorn listens on IPv4 only, and the IPv6-first lookup cost every new connection ~200 ms); set `VITE_API_BASE` to point elsewhere.
